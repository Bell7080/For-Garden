# 컨텐츠 종료·저장 왕복 검사 — 2026-10-20

수정 버전: **v0.320.8**. 새 SQL 마이그레이션이나 환경 변수는 없다.

## 제보와 현재 판단

- 기준 main: v0.320.7 (`9e07a138`), 공개 Vercel 클라이언트도 v0.320.7 확인.
- 3-10, 렉시아·메테·토리카 레벨 30, 자동 궁극기·2배속, Instagram Android 인앱 브라우저에서 「결과를 저장하지 못했습니다」 제보.
- 동일 문구는 발급·전투 검증·클리어 확정·결과 UI 오류에 공통 사용됐다. 사진만으로 운영 DB 장애/전투 재현 거절을 구분할 수 없다.
- 격리 환경에서 제보 편성의 클리어 저장·재조회는 성공했다. **제보 당시 운영 요청의 원인은 미확정**이다. 실제 Supabase/Vercel 함수 로그 및 계정 상태는 접근하지 않았다.

## 확인·수정한 복구 오류

1. 클리어 API가 성공한 뒤 결과판 생성이 실패하면 다음 재시도가 완료 API를 새 요청으로 보내 이미 소비한 전투 검증 기록으로 거절됐다. 전투별 성공 영수증을 보관해 결과판만 다시 만들며 새 전투에서는 초기화한다.
2. 이전 전투의 검증 응답이 재입장 뒤 도착하면 새 전투의 발급표를 지우고 이전 결과 UI를 열 수 있었다. 씬 세대와 발급표 일치를 확인한다. 늦은 클리어 응답도 새 전투의 영수증/UI를 건드리지 않는다.
3. 실패 화면에서 검증/저장/저장 후 표시를 구분하고 실패 단계·허용 목록의 원인 코드·클라이언트 버전을 확인할 수 있게 한다. 서버의 임의 원문, 저장 내용, 인증 정보는 출력하지 않는다.

첫 두 오류는 수정 전 실패/수정 후 통과하는 실제 BattleScene 제어 흐름 회귀로 확인했다. 이 오류들이 제보 당시 3-10의 직접 원인이었다고 확정하지 않는다.

## 검증 방식과 결과

- 최종 전체 단위 검사: **353개 파일 / 4,079 통과 / 1 skip**. 저속 소프트웨어 렌더링과 자원을 공유하므로 한 worker·30초 개별 제한으로 실행했다. 타입 검사·프로덕션 빌드와 서버 번들 생성도 완료했다.

- 실제 BattleScene `update`와 자동 궁극기 큐/기록 → JSON 저장 복원 → 서버 `finishCombat`: 편성 순서·1/2/3배속·시드·돌파 단계 조합 90건.
- 기존 레이드·원정·전투 검증 집중 검사 145건 통과.
- `node scripts/check-content-loops.mjs`: 외부 네트워크 없는 임시 PostgreSQL, 전체 마이그레이션, production 규칙으로 묶은 실제 `handleGameCall` + `RemoteGameApi` + `createSupabaseStore` 사용. HTTP만 로컬 SQL 호출로 대체해 실제 RPC 인자/응답과 JSONB 정규화를 통과한다. 운영 DB에 접속하지 않는다.
- 제보 편성/성장의 3-10 승리 → 검증 → 초회 보상/클리어 → 새 원격 API 인스턴스 재조회 통과.
- 별도 레벨 60 검사 편성으로 1-2/1-10/2-10/3-10/4-10 클리어 후 재조회 통과. 난이도 검사는 아니다.
- 레이드 입장 → 실제 전투 행동 재현 → 개인/공유 피해 DB 저장 → 재조회 → 시즌 종료 정산 → DB 정산 표식 확인 통과. 정산한 완료 판은 목록에서 숨기는 현재 정책을 함께 확인한다.
- 원정은 개발 바로가기 없이 1~20층의 증강 선택·전투·휴식·보물·보스 점수 제출·최종 정산을 진행해 활성 런 종료와 주간 최고점 재조회까지 통과.
- 전투 검증·클리어 확정·레이드 제출/정산·원정 점수 제출/최종 정산의 저장 직후 응답 유실을 주입해 모두 같은 요청 ID/서버 영수증으로 복구했다.
- 최종 실제 Chromium 브라우저 1/1 통과: 3-10 승리 → 서버 검증 → 보상/클리어 저장 → 결과판 → 지도 복귀 → 새로고침 후 SaveManager로 로컬 기록 유지 확인. 운영 규칙을 묶은 격리 메모리 서버에 연결한 검사이며 실제 Supabase 인증/운영 DB, Instagram WebView 검사는 아니다.

## 별도 잔여 항목

- 운영 원정 순위 목록: production `FakeServer.getExpeditionLeaderboard`는 빈 목록, 개인 최고점은 저장/조회된다. DB의 이용자 간 주간 순위 집계는 별도 서버 연결이 필요하다. 임의 순위를 만들지 않는다.
- 실제 Instagram WebView/운영 계정에 대한 동일 오류 재현은 미확인이다. 이번 검사 계정과 원본 계정의 룬·유대·돌파·배포 세션은 완전히 같지 않다.
- 새 SQL 마이그레이션/환경 변수 변경은 없다. 기존에 누락된 클리어를 추측해서 소급 추가하지 않는다.

## 다시 실행

- DB 전체 루프: Docker가 준비된 환경에서 `npm run test:content-loops`.
- 실제 씬 기록/복구 단위 검사: `npm test -- tests/unit/combatSceneReplay.test.ts tests/unit/battleResultRecovery.test.ts tests/unit/battleResultFailure.test.ts`.
- 브라우저 원격 왕복: `PF_E2E_REMOTE_LOOP=1 npx playwright test --config=playwright.remote.config.ts --project=functional-chromium --workers=1`. 별도의 Vite test 모드 서버를 쓰며 운영 규칙으로 묶은 격리 메모리 저장소에 연결한다. Supabase 인증/운영 DB는 모사하며, 실제 PostgreSQL 검사는 위 DB 루프가 별도로 담당한다. 반복 가능한 최종 종료/저장 검사는 실제 연출 스킵 설정을 사용한다. 일반 연출 실행도 실제 컷인 건너뛰기 탭으로 검증·클리어·결과창·지도 복귀에 도달했으나, 새로고침 검사에서 검사 코드의 저장 필드명 오류가 있어 그 실행 전체를 통과로 집계하지 않았다. 저장은 필드명을 직접 가정하지 않고 SaveManager로 검증한다.
