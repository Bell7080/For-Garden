# 공격 이펙트 좌표 오류와 전투 표시 비용 검토

검토 기준은 v0.284.6이며 수정은 v0.284.7에 반영했다. 전투 계산·배속·피해 판정은 변경하지 않았다.

## 공식 구현 대조와 선택

1. [Phaser 3.90 Tween.update](https://github.com/phaserjs/phaser/blob/v3.90.0/src/tweens/tween/Tween.js#L685)와 [TweenData.update](https://github.com/phaserjs/phaser/blob/v3.90.0/src/tweens/tween/TweenData.js#L264): onStart가 먼저 실행되고 pending-render 단계는 초기값 설정 후 반환할 수 있다. 따라서 첫 onUpdate 이전에도 렌더되는 표시 객체를 안전하게 준비해야 한다.
2. [Phaser 공식 풀링 탄환 예제](https://github.com/phaserjs/examples/blob/master/public/src/pools/bullets.js): fire에서 위치를 정한 뒤 active/visible을 켠다. group.get으로 재사용하고 화면 밖에서는 비활성화한다. 지연된 조각도 풀 슬롯을 예약하고, 표시 전에 시작 위치·각도·배율·알파를 확정하는 방식으로 적용했다.
3. [Unity 공식 ObjectPool 구현](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Runtime/Export/ObjectPool/ObjectPools.cs): Get/Release 초기화 콜백과 보관 상한을 둔다. Phaser의 기존 투사체 풀과 같은 생명주기 경계에서 근접 조각도 최대 32개만 보관하고, 상한에서는 가장 오래된 트윈을 중단한 후 슬롯을 재사용한다.

추가 타이머, 다음 프레임 대기, 화면 바깥 좌표 강제 보정은 사용하지 않았다. 첫 시작 상태를 즉시 적용한 뒤 기존 트윈 하나로 계속 이동한다. 임의 위치 보정은 정상적인 광역·넉백 표현까지 바꾸고 원인을 숨길 수 있어 채택하지 않았다. 엔진 버전이나 의존성도 추가하지 않았다.

## 수정한 낭비

- 근접 베기/발톱/물기는 매번 Image를 생성·파괴하던 것을 제한된 풀로 바꿨다. 지연 중에도 슬롯을 점유하며 씬 종료 시 트윈/이미지를 함께 정리한다.
- 투사체 꼬리는 새 발사 시 이전 좌표·각도·배율·알파를 남기지 않는다. 첫 프레임은 올바른 출발 좌표이며 꼬리 알파는 0에서 올라간다.
- 버프가 많을 때 `+N` 요약 칩을 매 프레임 파괴·생성하지 않는다. 구성/개수가 같으면 유지하고 최신 클릭 콜백만 갱신한다. 개수·제공자·효과/표현 종류가 달라지면 교체한다.
- 영구/조건부 버프 링과 유지 효과는 동일한 도형을 반복 작성하지 않는다. 시간형 진행률, 색·종류 변경은 반영하고 위치·방향·마스크 월드 좌표는 계속 따라간다.
- 카드 충전 비율이 동일하면 같은 부채꼴/폴리곤을 다시 계산하지 않는다. 비율을 양자화하거나 갱신 주기를 줄이지 않아 움직이는 게이지의 정밀도는 유지한다.
- 접힌 기여도 패널의 300ms 주기 스냅샷·행 갱신을 생략한다. 열기/카테고리 변경은 즉시 새로 계산한다.
- 전투의 매 프레임 QA 표시 스냅샷은 일반 빌드에서 만들지 않는다. QA/test/dev 빌드의 관찰 기능은 유지한다.

## 실제 브라우저 비교

Chromium WebGL/SwiftShader, 모바일 세로 390×844, 렉시아/루카/토리카의 쉬움 레이드, 궁극기 자동 OFF에서 약 16초의 코어 전투를 실행했다. 동일한 관찰 래퍼로 65회 update를 기록했다. 초기 asset 준비는 측정에서 제외했다. 원래 버전의 실전 렌더에서 1.74초에 `(0,0)`의 잘못된 공격 조각 두 개를 별도로 포착했다.

| 측정 | 수정 전 | 최종 수정 후 |
|---|---:|---:|
| 잘못된 `(0,0)`의 표시 조각 관찰 누계 | 44 | 0 |
| 새로 만든 잉크 이미지 전체(별/투사체 등 포함) | 84 | 53 |
| 근접 조각 풀 점유 최고/보유 수 | 생성·파괴 방식 | 14 (상한 32) |
| 접힌 기여도 갱신 함수의 누적 CPU 시간 | 49.6ms | 0.2ms |
| 전체 BattleScene.update 누적 CPU 시간 | 493.5ms | 497.5ms |
| 전체 BattleScene.update 평균 CPU 시간 | 7.59ms | 7.65ms |

버프 8개를 120번 전달한 별도 표시 경계 시험:

| 측정 | 수정 전 | 최종 수정 후 |
|---|---:|---:|
| 요약 칩 생성/교체 | 120 | 1 |
| 새 Graphics 수 | 615 | 20 |
| 총 CPU 시간 | 47.1ms | 2.6ms |

CPU 시간은 단일 전후 표본이며 브라우저·GC·소프트웨어 GPU 변동이 포함된다. 전체 update 시간의 소폭 차이를 성능 향상/악화의 확정값으로 해석하지 않는다. 안정적으로 확인한 이득은 잘못된 첫 프레임 제거, 객체 생성 감소, 보이지 않거나 변하지 않은 UI 작업의 제거다. 클라우드 소프트웨어 GPU의 FPS는 실제 휴대폰 FPS의 근거로 사용하지 않는다.

추가 회귀 확인: 베기/발톱/물기의 첫 visible 프레임, 투사체 풀 강제 재사용 시 꼬리의 새 좌표와 알파 0, 풀 상한/씬 정리, 요약 칩 최신 클릭 콜백·제거, 정적 버프 링의 재작성 0회, 실제 시간형 링 갱신, 같은 충전 비율 120회에서 재작성 0회와 카드 이동 시 마스크 추적, 유지 효과 이동·회전과 재작성 0회, 기여도 열기/카테고리 즉시 갱신을 검사했다. 단위 테스트와 실제 모바일 세로 캡처를 함께 사용했다.

## 남은 고비용 구간과 판단

- `IndexedPuppetCreature.renderWebGL`은 개체마다 Phaser 배치를 끊고 정점 버퍼를 올린다. 폭주 테두리/돌진 잔상은 같은 mesh를 겹 수만큼 추가 draw한다. 캐릭터가 많거나 잔상이 겹칠 때 GPU/드로콜 비용을 먼저 볼 지점이다. 위치·알파·컨텍스트 복구 경계를 임의로 생략하면 다른 UI까지 깨질 수 있어 이번에는 렌더러를 바꾸지 않았다.
- `stepMeters`의 움직이는 충전 마스크/체력·야성 UI와 `syncViews`의 Puppet 배치/상태 표시는 여전히 프레임별 작업이다. 정지 값만 캐시하고 실제 변화는 유지했다. 전체 전투에서 얼마를 차지하는지는 캐릭터 수·버프·기기별로 다시 측정해야 한다.
- `activeCombatBuffs`와 상태 뷰 구성은 여러 표시 경계에서 반복된다. 시뮬레이션 스텝 사이 또는 궁극기 즉시 변경까지 포괄하는 무효화 기준 없이 캐시하면 오래된 상태를 보여 줄 수 있어 이번에는 통째로 캐시하지 않았다.
- 아직 미리 읽지 않은 Puppet/컷인 자산의 최초 다운로드·ZIP 해제/텍스처 업로드는 별도의 첫 사용 지연 후보이다. 이번 전후 비교는 asset 준비 이후의 비용만 다룬다. 모든 자산을 일괄 선로딩하면 시작 시간·메모리를 늘리므로 실제 기기의 cold/warm 추적 없이 확대하지 않는다.
