# 계정 생성·게스트 연동 — v0.321.1

## 확인한 문제와 변경

기존 `SupabaseAccountApi.registerWithId`는 신규 가입에 `/auth/v1/signup`, 게스트 승격에 `/auth/v1/user` 이메일 변경을 사용했다. 게임은 메일 없는 합성 아이디(`id.forgarden.app`)를 전제로 하지만, 이 경로는 Supabase 메일 확인/발송 설정의 영향을 받는다. 세션 없는 가입 응답도 일반 네트워크 오류로 표시했다. 운영 Auth 로그를 읽을 권한은 없어 제보 당시 응답 코드·원인은 확정하지 않는다.

메일 없는 가입/승격은 새 서버 API `/api/account`가 맡는다. 기존 서비스 역할 키로 확인 완료 계정을 생성하거나, **Bearer로 확인한 본인 게스트 UID**만 승격한다. 사용자 입력 UID는 사용하지 않는다. 다른 계정의 아이디가 이미 있으면 덮어쓰거나 자동 로그인하지 않는다. 서비스 키·비밀번호·토큰은 응답/로그에 남기지 않는다.

Supabase 공식 구현에서 관리자 비밀번호 변경은 기존 세션을 종료한다. 따라서 승격 후 구형 refresh 토큰을 재사용하지 않고 새 비밀번호로 로그인한다. 반환 UID가 가입/승격 UID와 일치하는지 검사한다. 가입 응답 후 로그인만 실패한 재시도는 확인된 같은 UID에 대한 로그인만 재시도한다(비밀번호는 저장하지 않음). 이 메모리가 사라진 경우 로그인 탭에서 입력한 아이디로 접속할 수 있다.

추가로 기존 refresh는 요청 제한·네트워크 오류에도 게스트 토큰을 지웠다. 이제 실제 폐기된 refresh만 지우고, 일시 오류/429에서는 보존한다. 새 토큰의 보관에 실패하면 메모리 계정을 먼저 바꾸지 않는다.

## 기존 미확인 아이디 복구

이전 메일 경로에서 생성됐지만 확인되지 않은 합성 아이디는 로그인에서 복구한다. 공식 GoTrue는 비밀번호 검증에 성공한 뒤 `email_not_confirmed`를 반환한다. 서버가 이 응답을 직접 다시 확인한 경우에만 정확한 합성 이메일의 UID를 조회하고 확인 처리한다. 잘못된 비밀번호는 UID 조회/확인에 도달하지 않는다. 비밀번호를 덮어쓰거나 새 UID를 만들지 않는다. 로그인은 이후 다시 수행하고 같은 UID인지 검증한다. 게스트 연동에서 기존 계정으로 들어가는 경고/확인은 그대로 거친다.

## 팝업·진행 전환

- 설정의 연동도 상단 로그인/회원가입 탭을 항상 표시한다.
- 회원가입: 현재 게스트 UID/서버 진행 그대로 아이디·비밀번호를 추가한다.
- 로그인: 현재 게스트 진행을 사용하지 않고 기존 계정으로 이동하며, 게스트 재접속이 어려워질 수 있다는 확인을 먼저 받는다. 성공했을 때만 기존 연결/로컬 저장을 걷고 Boot에서 로그인 계정의 서버 진행을 읽는다. 취소·실패는 현재 게스트 진행을 지우지 않는다. 서버의 게스트 저장 자체를 삭제하거나 두 진행을 합치지 않는다.
- 인증 중 탭 전환·중복 제출/닫기 버튼을 막는다. 오류는 다시 입력할 수 있도록 잠금을 해제한다. 가입/로그인 대기는 따로 관리하여 가입 제한이 로그인을 막지 않는다.
- 이전 서버 연결의 늦은 응답은 계정 전환 후 진행이나 API 설치 상태를 덮지 못한다.

## 속도 제한

`server_take_account_rate`는 기존 `support_limits` 표에 원본 IP 대신 서비스 비밀값으로 해시한 키를 저장한다. Vercel이 설정하는 접속 IP와 인증 UID 각각 분당 5회/시간당 20회의 가입 제한을 적용한다. 인증 서버 호출 전에 IP 제한을 확인하며, 제한 저장소 장애 때는 가입을 실행하지 않는다.

429에 실제 남은 `Retry-After`를 보내고 UI에 초를 표시한다. **거절된 재시도는 기록을 더하지 않아 대기가 계속 연장되지 않는다.** Auth 자체가 반환한 429도 대기 헤더가 있으면 표시한다. Auth 전체 제한을 끄거나 무제한 재시도를 하지 않는다.

## 적용

1. `supabase/migrations/20261028000000_account_registration.sql` 적용.
2. v0.321.1 서버/클라이언트 배포. `npm run build:server`가 `api/game.js`와 `api/account.js`를 생성한다.

기존 `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`와 클라이언트 publishable 키를 사용한다. 별도 SMTP/메일 발송 설정은 필요 없다. Supabase Email/password 제공자는 활성 상태여야 한다. 실제 이메일 연동·구글·애플·다중 identity 연동은 이 패치에 추가하지 않는다.

현재 환경에는 운영 Supabase 관리 키/도구가 없어 **운영 마이그레이션 적용·실계정 가입은 실행하지 않았다.** 이전 PvP용 26/27 마이그레이션이 아직이라면 기존 파일부터 순서대로 적용한다. 출시 초기화 스크립트를 기능 적용 목적으로 실행하지 않는다.

## 검증

- `npm run test:account-db`: 전체 마이그레이션을 올린 격리 PostgreSQL. 분당/시간당 제한, 거절 재시도의 기록 수 불변, 시간 경과 뒤 실제 허용 복구, anon/authenticated RPC 직접 실행 금지 확인.
- 계정 API/서버 단위 검사: 같은 UID 승격, 확인 메일 없는 관리자 호출, 임의 UID 무시, 기존 아이디 거절, 제한의 Retry-After, 일시 refresh 실패 시 게스트 보존, 가입 후 로그인 응답 유실 복구.
- 설정/연결 검사: 로그인 성공 때만 로컬 진행 교체, 가입 시 유지, 이전 응답의 진행 덮기/설치 방지.
- 브라우저: 실제 연동 팝업의 두 탭, 입력·중복 제출 차단, 가입 제한 후 로그인 선택, 기존 계정 전환 취소·실패·성공. 인증 서비스 응답은 주입하므로 운영 Auth 동작의 검증과 구분한다.

공식 동작 참고: https://github.com/supabase/auth/blob/master/internal/api/admin.go 및 https://github.com/supabase/auth/blob/master/internal/models/user.go (`UpdatePassword`의 세션 종료).
