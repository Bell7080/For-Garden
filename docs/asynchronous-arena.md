# 비동기 방어전 설계

## 제품 범위와 출시 순서

비동기 방어전은 실시간 네트워크 대전이 아니다. 공격자는 서버에 저장된 상대의 방어 편성
스냅샷을 받아 기존 `src/core/skirmish.ts` 규칙으로 싸우고, 서버가 같은 입력을 다시 실행해 결과를
확정한다. **이벤트 운영과 기본 경제가 안정된 뒤 진행하는 별도 마일스톤**이며 초기 출시의
`GameApi`, 화면, 저장 데이터에는 넣지 않는다.

이 순서는 경쟁 콘텐츠가 재화 원장, UTC 경계, 운영 기간 장애를 증폭시키지 않게 한다. 구현 착수
조건은 이벤트 기간 전환·보상 회수, 기본 재화 원장의 원자적 저장, 전투 규칙 버전 보존이 운영에서
검증된 상태다.

## PvP 진입 화면과 모드 범위

현재 PvP 진입 화면은 네 모드의 성격과 예정 범위를 고르는 **기획 안내용 진입점**이다. 모드를
선택해도 매칭 티켓, 전투, 점수 또는 보상을 만들지 않는다. `PvpScene`과 `PvpPreviewScene`은 이
경계를 유지하며, 아래에서 서버 권위가 필요하다고 적은 모드는 백엔드 계약과 운영 정책이 준비된
후에만 실제 시작 조작을 연결한다.

### 우두머리 결정전 표시 정책

준비된 풀을 “매칭 중인 이용자”, “실시간 상대” 또는 그와 동등한 표현으로 포장하지 않는다. 화면에는
상대를 **NPC 도전자**, **기록 편성**처럼 실제 출처에 맞춰 표시하고, 기록 데이터라면 기록 시점과
운영 제공 데이터 여부를 이용자가 구분할 수 있게 한다. 검색 대기 애니메이션을 쓰더라도 그것은
후보를 고르는 처리 상태만 나타내야 하며, 다른 이용자가 지금 접속해 응답하고 있다는 인상을 주면
안 된다. 실제 이용자 간 실시간 매칭은 동시 접속, 연결 복구, 판정 서버와 부정행위 방지 범위를
새로 합의하는 후속 마일스톤에서만 다룬다.

## 서버 권위 상태

네트워크 DTO 초안은 `src/api/asyncArenaContracts.ts`에 둔다. 백엔드는 다음을 영속 상태로 소유한다.

- **방어 편성 스냅샷**: 정확히 세 유닛의 ID, 순서, 레벨, 유대, 각성, 장착물과 전투/정적 데이터
  버전을 저장한다. 방어 편성을 다시 게시해도 진행 중 티켓이 참조하는 옛 스냅샷은 만료까지 보존한다.
- **주간 점수**: 서버가 만든 `weekId`, 점수, 승패, 갱신 시각을 함께 저장한다. 주간 교체와 동점
  정렬은 서버 UTC 시각만 사용한다.
- **일일 도전 횟수**: 서버 UTC 날짜, 사용량, 한도를 저장한다. 티켓 발급 시 한 번 예약하고,
  만료·취소 정책으로만 반환해 다중 기기 동시 발급을 막는다.
- **시즌 보상**: 시즌, 최종 티어, 보상 목록, 수령 상태를 저장하고 수령을 멱등 처리한다.

## 전투 프로토콜

1. **방어 게시**: 서버가 보유, 중복 유닛, 정확히 3명, 성장 범위와 장착 소유권을 검사한 뒤 불변
   스냅샷을 만든다. 클라이언트가 계산한 능력치 합계는 받지 않는다.
2. **상대 조회**: 서버는 자기 자신과 최근 상대를 제외하고 점수대 후보를 고른다. 목록에는 공개용
   프로필과 스냅샷 요약만 주며 내부 플레이어 상태는 노출하지 않는다.
3. **전투 발급**: 서버가 공격자도 현재 상태에서 스냅샷으로 고정하고, 상대 스냅샷, 규칙 버전,
   예측 불가능한 난수 시드, 만료 시각, 일회성 제출 토큰을 묶은 티켓을 저장한다.
4. **로컬 실행**: 클라이언트는 티켓으로 `createSkirmish`를 만들고 고정 틱으로 `stepSkirmish`를
   실행한다. 전송을 위해 기록하는 값은 궁극기 발동의 `tick/sequence/slot`뿐이다.
5. **결과 제출**: 클라이언트는 `battleId`, 토큰, 결정 로그만 보낸다. 승패, 피해량, 종료 시간,
   점수 증감, 보상은 요청 필드에 존재하지 않는다.
6. **서버 확정**: 서버는 저장 티켓을 읽어 같은 규칙 버전과 시드로 전투를 처음부터 재생한다.
   재생 결과가 종료된 경우에만 도전 횟수와 주간 점수를 한 트랜잭션으로 확정하고 결과 DTO를 만든다.

`Math.random()`의 구현 차이를 피하려면 시드를 숫자열로 바꾸는 PRNG와 20 Hz 같은 고정 틱을 서버와
클라이언트가 공유해야 한다. 현재 `stepSkirmish`의 부동소수점 계산이 서로 다른 런타임에서도 같은지
검증하기 전에는 서버 런타임을 웹과 같은 JavaScript 구현으로 고정한다. 규칙이 바뀌면 기존 티켓은
그 티켓의 `rulesVersion` 구현으로만 재생하고, 지원 기간이 끝나면 안전하게 무효화한다.

## 서버 검증과 악용 방지

- 티켓의 계정, 만료, 미사용 토큰, 양쪽 스냅샷 해시와 규칙 버전을 먼저 확인한다.
- 명령은 개수 상한을 두고 `sequence`와 `atTick`의 엄격한 증가, 유효 슬롯, 해당 틱의 생존·게이지·
  전투 진행 상태를 검사한다. 불가능한 궁극기나 종료 뒤 입력은 전체 제출을 거절한다.
- 서버 시드에서 난수열을 만들며 클라이언트 시드, 프레임 시간, 최종 상태 해시는 신뢰하지 않는다.
- `battleId`에 결과를 유일하게 저장한다. 같은 제출은 저장된 결과를 반환하고 다른 로그로 다시
  제출하면 거절해 도전 횟수와 점수의 이중 반영을 막는다.
- 타임아웃, 명령 수, 본문 크기, 티켓 발급 빈도 제한을 둔다. 비정상 로그와 재현 실패는 점수를
  바꾸지 않고 감사 로그에 남긴다.
- 상대 방어 결과는 방어자 점수에 직접 반영하지 않는다. 첫 단계는 공격자 개인 점수만 바꿔
  매칭 저격, 합의 승부, 오프라인 불이익을 줄인다.

## 점수와 보상 원칙

점수 공식은 서버 운영 데이터로 버전 관리하고 승리 증가·패배 감소에 상한을 둔다. 매칭 상대의
현재 점수가 아니라 티켓 발급 시 고정한 점수 구간을 사용한다. 시즌 종료 작업은 최종 티어를 먼저
동결한 뒤 보상 레코드를 생성하며, 생성과 수령은 각각 재실행해도 중복 지급되지 않아야 한다.

보상은 **프로필 프레임, 칭호, 소량의 치즈케이크 또는 골드**로 제한한다. 전용 캐릭터, 한정 성능 장비,
돌파·각성 등 필수 성장 재료, 경쟁 참여를 강제할 만큼 많은 범용 재화는 지급하지 않는다. 구체적인
소량 상한은 기본 경제의 주간 획득량이 안정된 뒤 경제 문서에서 정하며, 그 전에는 값 자체를 넣지 않는다.

## 후속 구현 체크리스트

- `skirmish.ts` 입력을 고정 틱 명령으로 감싸는 순수 리플레이 실행기와 골든 벡터 테스트
- 규칙/정적 데이터 버전 레지스트리, 만료된 버전의 티켓 종료 정책
- 데이터베이스 유일 키(`battleId`, 시즌 보상 수령)와 원자적 점수·횟수 갱신
- 매칭 반복·자기 계정·다중 계정 악용 완화와 운영 감사 도구
- 이벤트와 경제 안정성 지표가 충족된 뒤에만 `GameApi`와 화면을 연결하는 기능 플래그

## 임시·잔여 코드 확인

이 설계 변경은 실행 경로, 테스트 더블, 임시 화면을 추가하지 않는다. 계약 파일은 후속 서버 구현을
위한 의도적인 비활성 설계 산출물이며, 마일스톤 착수 때 실제 API 계약으로 승격하거나 삭제해야 한다.
