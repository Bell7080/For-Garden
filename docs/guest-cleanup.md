# 유령 게스트 계정 정리

게스트(익명) 계정의 열쇠는 그 기기에 든 토큰 하나다. 토큰을 버리면(계정 변경·앱 삭제·브라우저 데이터 삭제) 아무도 그 계정에
다시 들어갈 수 없는데, 서버에는 계정이 `active`로 남아 친구 추천·검색에 이름 없는 Lv.1로 선다. 리세마라가 늘면 이 계정이 쌓인다.

## 판정 기준

| 경우 | 서버가 아는가 | 처리 |
| --- | --- | --- |
| 게스트가 타이틀 「계정 변경」으로 로그아웃 | 안다 — 로그아웃이 `abandon_guest_account`를 부른다 | 곧바로 `status='deleted'`(모든 노출 경로에서 빠짐) → 하루 유예 뒤 `purge-deleted-accounts`가 삭제 |
| 앱 삭제·브라우저 데이터 삭제·알림 실패 | 모른다 | `purge_inactive_guests(일수)` — 마지막 활동(가입·로그인·서버 저장 중 가장 늦은 것)이 기준 일수보다 오래된 게스트 |

**보호 조건(어느 경우든 지우지 않는다)**

- 연동 계정(`auth.users.is_anonymous`가 false) — 판정은 클라이언트가 아니라 서버가 한다.
- 운영진(`admin_roles`).
- 결제 기록(`purchase_records`)이 있는 게스트 — 로그아웃하면 감추기만 하고 지우지 않는다(환불·분쟁 기록 보관). 오래 안 들어와도 대상이 아니다.

**함께 정리되는 것:** `auth.users`를 지우면 외래키 연쇄로 진행·친구·즐겨찾기·길드 멤버·아레나·랭킹 기록이 함께 지워진다.
길드장이면 `players_release_guild` 트리거가 부길드장 → 임원 → 길드원 순으로 넘기고, 남은 사람이 없으면 길드를 지운다.
레이드 소유자 칸은 비워진다(`set null`).

## 운영에서 쓰는 SQL (서비스 역할)

```sql
-- 미리보기: 지우지 않고 수와 UID만 본다
select public.purge_inactive_guests(180);            -- p_dry_run 기본 true
select * from public.inactive_guest_candidates(180);  -- 줄마다 UID·이름·레벨·마지막 활동
-- 실제 삭제(되돌릴 수 없다 — 응태 승인 뒤)
select public.purge_inactive_guests(180, false);
```

정기 실행이 필요하면 승인된 일수로 pg_cron에 건다(예: `cron.schedule('purge-inactive-guests', '30 3 * * *', 'select public.purge_inactive_guests(180, false)')`).
지금은 **예약하지 않았다.**

## 업계에서는

- **로그아웃 전에 경고하고, 연동을 먼저 권한다.** 게스트 계정은 로그아웃·앱 삭제 시 복구 불가라는 안내가 거의 모든 모바일 수집형의
  표준이다(우리도 확인 창에 적는다).
- **미연동 게스트는 비활성 기간 뒤 자동 삭제.** 흔한 기준은 90~365일 미접속이고, 결제 이력이 있는 계정은 제외하거나 훨씬 길게 둔다.
  개인정보 보호법상 장기 미이용자 정리(1년 기준 분리·파기)와도 맞물린다.
- **추천·랭킹은 최근 활동자만.** 친구 추천은 보통 최근 7~14일 접속자, 랭킹은 시즌 참여자만 올린다(우리 추천은 14일).
- **리세마라 계정 대응**은 삭제보다 노출 차단이 먼저다 — 저레벨·무명·미연동 계정을 추천·검색에서 빼고, 기기/계정 생성 속도를
  제한하며, 일정 기간 뒤 정리한다. 가입 속도 제한은 Supabase 익명 로그인 한도(시간당 IP 기준)가 이미 맡고 있다.
