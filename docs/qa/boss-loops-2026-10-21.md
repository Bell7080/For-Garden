# 레이드·원정 점수/보상 루프 점검 (v0.323.2)

## 재현된 결함

### 자발적 퇴장의 종료 시점 누락

화면은 일시정지 → 나가기에서 현재 피해로 전투를 종료하지만 제출 계약에는 궁극기 입력만 있었다. 확정 재현은 입력 이후에도 자연 전멸까지 진행하므로, 벽시계 검사가 `COMBAT_TOO_FAST`로 거절하거나 기다린 뒤 재시도하면 실제로 하지 않은 나머지 전투의 점수까지 계산할 수 있었다. 레이드와 원정이 같은 재현기를 써서 양쪽 모두 영향을 받는다.

신규 클라이언트는 자발적 종료일 때만 `stopAtMs`를 함께 보낸다. 서버가 입장/런의 시드·성장 스냅샷과 실제 전투 코어로 그 틱까지만 계산한다. 음수·소수·20ms 틱 사이·최대 시간 초과와 종료 이후 입력은 거절하며, 기존 벽시계/게이지/행동 검증도 유지한다. 자연 종료 제출은 기존 계약을 유지한다. 클라이언트가 피해 합계를 결정하는 통로는 추가하지 않았다.

### 저장 완료 후 새 클라이언트에서 점수 영수증 복구 실패

점수 커밋 후 응답을 두 번 잃고 새 RemoteGameApi에서 같은 내부 입장 ID로 다시 제출하면, 내부 `raidSubmit` 영수증은 복구되지만 최초 커밋 때 소진한 입장 영수증이 없어 벽시계 검사에서 `COMBAT_TOO_FAST`가 발생했다. 실제 PostgreSQL + strict handler에서 재현했다. 서버가 이미 확정한 동일 레이드/런의 내부 영수증 응답은 새 전투가 아니므로 재검증하지 않도록 수정했다. 다른 레이드/런 ID에 해당 영수증을 쓰는 요청과 미확정 전투는 계속 거절한다.

## 검사 층위

1. 실제 공용 전투 코어와 서버 재현의 왕복 검사: 레이드 보스 3종 × 난이도 4단계 × 편성 6종 × 1/3배속, 원정 편성 6종 × 1/3배속 × 자동 궁극기 켬/끔. 긴 프레임, 소환수, 공격/지원 궁극기, 폭주를 포함한다. 이 신규 조합은 태생 능력치를 사용하며 성장 스냅샷은 아래 DB/브라우저 검사에서 별도로 확인한다.
2. 전체 운영 마이그레이션을 적용한 임시 PostgreSQL + 실제 SupabaseStore RPC 인자/JSONB + strict handler + RemoteGameApi. 실제 HTTP 전송만 로컬 RPC 브리지로 대체한다. 운영 Supabase에는 접속하거나 쓰지 않는다.
3. 별도 PostgreSQL 연결의 실제 동시 RPC: 같은 공유 revision의 동시 제출 중 하나만 성공, 실패한 쪽 재조회/재시도, 계정 저장 실패 시 공유 HP 변경도 롤백.
4. Chromium 실제 화면: 레이드 자연 종료, 레이드·원정 일시정지 → 나가기 → 저장 장애 → 결과 다시 확인. 제품의 실제 버튼을 클릭하며 전투 시간·점수는 강제로 바꾸지 않는다. 원정 화면의 준비 상태는 보스 직전 fixture이며 전체 20층 플레이는 DB 루프가 검사한다.

## DB 시나리오

| 조건 | 확인 항목 |
| --- | --- |
| 10초 중도 퇴장 | 종료 틱까지 화면의 실제 피해와 서버 점수 일치 |
| 공유 revision 충돌 | 새 context로 재시도, 한 번만 반영 |
| 저장 전 장애 | 공유 HP·개인 기여·지갑·입장 보존 |
| 커밋 후 응답 2회 유실 | 새 클라이언트/새 HTTP ID에서 기존 내부 영수증 복구 |
| 두 계정 참가 | 각 개인 기여/참가자 목록을 재조회하고 DB 멤버 행과 대조 |
| 두 입장 이후 다른 참가자가 HP를 1까지 감소 | 마지막 두 제출의 공유 차감 1/0, 각 개인 피해는 입장 시 유효한 만큼 보존 |
| 최종 레이드 보상 | 실제 지갑 증가량 = 지급 영수증, 동일 키 재접속 수령도 한 번만 지급 |
| 원정 점수 저장 실패 | 진행/최고점/노드 방문/영수증 미반영 |
| 원정 점수 커밋 후 응답 유실 | 재접속 후 동일 최고점과 보스 방문 복원 |
| 원정 점수 성공 후 최종 정산 장애 | 점수 중복 없이 최종 보상만 재시도, 활성 런 종료 |
| 원정 최고점/랭킹 | 주간 최고점·DB 랭킹의 점수 일치, 최종 보상과 중복 수령 대조 |
| 정상 원정 전체 경로 | 1층부터 20층까지 증강/전투/휴식/보스/최종 정산/재조회 |

공유 HP보다 개인 피해 합계가 커질 수 있는 것은 동시 처치 경계에서 유효한 개인 전투를 보존하는 기존 규칙이다. 공유 HP는 0 아래로 내려가지 않는다. 매번 점수만큼 공유 HP를 중복 차감하지 않는다.

## 실행 결과

- 집중 6파일 300개 통과. 전체 367파일은 4307개 통과·1개 건너뜀·2개 실패였으며, 두 실패는 기존 씬 초기화 도우미가 이번에 읽게 된 전투 상태/틱 상수를 주입하지 않은 경우였다. 실제 전투 상태를 넣도록 고친 뒤 해당 파일과 보스/서버 경계 194개, 마지막 씬 복구 검사 4개가 통과했다. 제품 로직을 우회하도록 도우미를 바꾸지 않았다.
- 최신 전체 마이그레이션 PostgreSQL 루프 통과. 예시: 레이드 자연 종료 개인 피해 7,735 저장/정산, 원정 20층 총점 973,283 저장/최고점 재조회/최종 정산, 별도 원정 10초 퇴장 총점 96,210·골드 300·랭킹 반영. 각 fixture의 성장/일반 노드 점수와 난수 시드가 달라 사례 간 수치 자체를 비교하지 않는다.
- 별도 PostgreSQL 동시 연결의 공유 revision 충돌/재시도·부분 커밋 롤백 검사 통과.
- 화면 E2E 3흐름 통과: 레이드 출격/편성/자연 종료/저장/복귀, 레이드 퇴장/저장 실패/재시도, 원정 퇴장/점수 성공/정산 실패/재시도/로비 복귀. 최초 검사기의 버튼 문구와 원정 전용 결과 관측값을 현행 화면에 맞추고 해당 편만 재실행했다.
- 정상 레이드 화면 증빙에서 점수 3,500·골드 700이 표시된다. 이미지와 DB/단위/E2E 로그는 `/workspace/reports/forgarden-boss-loops-2026-10-21/`에 보관했다.

- TypeScript·서버 생성·정식 빌드 및 최신 산출물의 일반/QA/test 격리 검사 통과.

## 제한과 배포

- 로컬 임시 DB와 source E2E 결과다. 운영 Vercel 로그·실제 Supabase의 적용 버전·실제 네트워크 장애 빈도를 직접 확인한 것은 아니다.
- 모든 기기/편성/레벨/장비/일시정지 조합을 전수 검사하지 않았다. 큰 서비스 부하 시험도 아니다.
- 요청 필드 추가 및 서버 검증 수정이며 저장 형식/SQL 변경은 없다. 별도 마이그레이션은 필요 없고 서버와 클라이언트를 함께 배포해야 한다.
- 이미 확정된 기록을 다시 가산하거나 과거 실패분을 추측해 소급 지급하지 않는다. 미확정 퇴장 기록은 과거 종료 틱이 저장되어 있지 않아 복원할 수 없다.
