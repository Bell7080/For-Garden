## API 변경과 실제 연동 시 주의

- `SubmitExpeditionBossScoreResponse.rankAfter`는 `number | null`이다. 실제 순위표가 없으면 점수가 있어도 null이다. 숫자 1·0으로 미확인 순위를 대신하지 않는다. 점수 구성·개인 최고점과 달성 보상은 그대로다.
- 모의 결투 조작은 `DUEL_UNAVAILABLE`로 거절한다. UI의 기존 진입점·방어덱 편성은 유지한다. 실제 상대 어댑터가 연결되면 진짜 프로필/방어덱·시즌/기록·순위·보상으로 구현해야 하며, production의 QA 스위치를 켜서 우회하지 않는다.
- 이전에 저장된 점수·시즌 대기 기록·수령 이력은 이번 변경으로 삭제하지 않는다. 모의 순위 보상 생성·수령 경로를 차단한다. 이전 테스트 계정/서버 기록을 실제 운영으로 이관하는 정책은 별도 검증이 필요하다.
- 고정 환영 보상의 재화량과 원문은 QA에서 볼 수 있다. 실제 출시 선물로 지급하려면 서버 운영 우편에 대상·기간·멱등/수령 기록을 갖추고 등록한다. 기존 로컬 IDs를 서버 운영 지급과 혼동하지 않는다.
- FakeServer를 호출하는 서버에도 기본 검증기의 거절 정책이 적용된다. 실제 광고 SSV와 Apple/Google 영수증 검증을 연결할 때 `verifyAdToken`·`verifyPurchaseReceipt`를 주입하고 재전송/거래 중복 검증을 서버에 유지해야 한다. 문자열 접두사를 서명으로 취급하지 않는다.

## 검증

- `npm run test:release-fixtures`: 실제 소스를 production/qa/test로 각각 컴파일해 호출한다. 일반에서 NPC와 방어전이 없는지, 충분한 재화와 가짜 이전 시즌 보상을 주어도 모의 조작이 상태/지갑을 바꾸지 않는지 확인한다. 없는 우편 ID를 직접 수령 요청해도 지급되지 않아야 한다.
- 같은 검증에서 일반의 개인 점수 달성 보상, 실제 검증기 주입, 검증된 구독 우편이 유지되는지도 확인한다. QA 표본과 테스트 결제 흐름은 QA/test에서 여전히 동작해야 한다.
- `npm run build` 뒤 `npm run test:build-isolation`로 기존 저장/디버그 분리를 함께 재검증한다. 모든 단위 검사·타입 검사·클라이언트/서버 빌드도 수행한다.
- 화면 배치와 진입점은 바꾸지 않았으며 전체 E2E나 운영 DB 쓰기는 수행하지 않는다.

## 출시 차단 — 웹 토큰 보관소(`src/api/webTokenStore.ts`)

- 웹 빌드는 게스트 로그인 토큰을 `localStorage`에 둔다(v0.296.1, 응태 결정). 플레이어와 결제가 없는 출시 전에만 허용한 임시 예외다.
- **결제가 붙기 전, 정식 출시 전에 반드시 없앤다.** 앱 빌드는 키체인/키스토어 어댑터를 `TokenStore`로 주입하고, 남는 웹 배포는 HttpOnly 서버 세션으로 바꾼다. 그 뒤 `webTokenStore.ts`·`installBackend`의 기본 보관소·CLAUDE.md의 예외 문단을 함께 지운다.
- 게스트는 기기를 잃으면 계정을 되찾을 수 없으므로 소셜 연동도 같은 시점의 선행 조건이다.

## 출시 전환 점검 — 테스트 계정이 운영에 섞이지 않게

- 운영 Supabase 프로젝트(`forgarden-prod`)는 출시 직전에 **새로 만든다**. 테스트 프로젝트의 계정·토큰은 운영에서 쓸 수 없다(낡은 토큰은 거절되고 게임이 지운 뒤 새 게스트로 시작한다).
- 실서비스 Vercel 프로젝트(포가든)의 `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`·`VITE_SUPABASE_*`는 지금 테스트 DB 값이다. **출시 직전에 운영 프로젝트 값으로 바꾸고 재배포한다.**
- 베타 기기에 남은 로컬 저장이 새 운영 서버로 올라가지 않도록 **출시 때 로컬 저장 키를 교체(일괄 초기화)한다**(`src/core/saveStorage.ts`의 production 키). 같은 주소를 계속 쓰는 베타 기기에서 진행이 섞이는 것을 막는다.
