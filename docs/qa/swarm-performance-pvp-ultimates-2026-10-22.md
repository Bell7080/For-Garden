# 물량전 표시 비용·PvP 궁극기 점검 (v0.323.5)

## 확인한 차이

- `spawnFighters`는 전원이 준비된 뒤 전투를 시작하지만, `spawnPuppet`이 먼저 만든 개체는 그 이전부터 활성/가시 상태로 씬의 UPDATE·렌더에 참여했다. 15적과 아군/소환수의 초기화가 준비 중인 모델의 스키닝·그리기와 겹쳤다. 병렬로 끝난 모델의 메인 스레드 생성도 한 덩어리로 몰릴 수 있었다.

- 폭주 테두리는 한 개체마다 먹선 12겹·붉은 띠 12겹을 원본 indexed mesh로 다시 그렸다. 여러 적이 함께 폭주하면 draw·행렬 합성·uniform 배열 할당이 개체 수와 24겹만큼 늘었다.
- 체력 바는 HP·잔상·보호막 값이 그대로여도 매 프레임 도형을 다시 만들었다. 빈 상태 칩과 멈춘 시계, 상태 입력면도 반복 갱신했다.
- PvP 성장 능력치는 양쪽 모두 `RelicProgressionManager.getFinalStats`를 사용하며 방어팀 전용 감산은 없었다. 그러나 공격팀 궁극기는 씬 대기열의 `fireUltimate`, 방어팀은 일반 공격의 쿨다운/사거리 뒤 `strike`를 사용했다. 순수 지원·회복 궁극기는 `strike`의 비공격 스킬 반환 조건 때문에 실제 효과가 실행되지 않았다.

## 수정

- 다운로드·파싱은 병렬로 두고 모델 생성·텍스처 준비만 `PuppetCreationQueue`로 나눈다. 누적 작업 경과가 8ms를 넘으면 다음 화면 갱신에 제어를 돌려준다. 한 모델 작업 자체의 실행 시간을 8ms 이하로 강제한다는 뜻은 아니다.
- 양보는 브라우저 작업 큐로 넘긴다. GPU가 느릴 때 rAF 한 프레임의 완료를 매번 강제 대기해 초기화 대기를 누적시키지 않는다.
- 부분 생성 모델은 전원이 준비될 때까지 숨기고 애니메이션을 정지한다. 준비 완료 후 함께 표시하며 그때 전투 시계를 시작한다. 씬 종료/세대 변경은 대기 중인 생성과 늦은 화면 등록을 취소한다.

- 생존 개체가 10명을 넘으면 폭주 테두리를 각 6방향으로 그린다. 24회 복제를 12회로 줄이면서 먹선·붉은 띠·몸 채움·사이렌·빠직 표식은 유지한다.
- 잔상마다 GameObject 좌표를 바꿔 행렬을 다시 합성하지 않는다. Phaser `GetCalcMatrix`가 제공하는 부모·카메라 축으로 변위만 합성하며, 본체 행렬 계산은 개체당 한 번이다. 본체/잔상용 Float32Array 두 개는 개체 수명 동안 재사용한다.
- 체력 바의 실제 채움이 바뀔 때만 재그린다. 반복된 HP 입력과 정지한 보간 상태는 객체도 재사용한다. 빈 상태 목록·같은 시계 값·입력 활성화도 변화가 있을 때만 갱신한다. 사망 시 입력 캐시를 비워 재소환 후 입력을 복원한다.
- 새 PvP 발급표는 `automaticUltimates`를 포함한다. 양쪽 편성 궁극기를 공용 전투 코어의 같은 고정 스텝과 `fireUltimate`로 실행해 평타 쿨다운·사거리·씬 프레임·컷인 대기열에 발동을 맡기지 않는다. 기절·생존·게이지 조건은 같은 `canFireUltimate`로 검증한다.
- 새 자동 전투 발급표는 수동 행동 기록을 거절한다. 기존 발급표는 기존 규칙을 유지하며, 기존 PvE와 귀속 소환수의 자동 발동 경로는 유지한다. 서버 번들도 같은 코어로 생성한다.
- 준비 요청의 클라이언트 지원 표시로 새 PvP 규칙을 협상한다. 업데이트 전부터 열려 있던 구형 클라이언트와 이미 발급된 전투는 기존 방식으로 계속 검증한다.

## 확인 결과와 한계

- 최종 `npm run typecheck`, `npm run build`, `npm run build:server`, QA/일반 빌드 분리·출시 fixture 검사, `npm run test:pvp-db`를 통과했다. 전체 검사는 `npm test -- --testTimeout=20000 --maxWorkers=1 --no-file-parallelism`으로 373개 파일·4,441 통과·1 제외, 검사기 오류 없이 종료했다. 앞선 동시 실행에서는 항목은 통과했으나 Vitest `onTaskUpdate` 통신 시간 초과가 발생해 무거운 브라우저/빌드를 종료하고 단독 재검사했다.

- 최종 시작 구간의 실제 모델 30개 생성, 작업 큐 양보 18회, 준비 완료 전 애니메이션 계산 0회를 확인했다. 메인 스레드 단일 모델 작업은 이 측정 환경에서 최대 37ms였으며 8ms는 여러 작업을 묶는 예산이다. 단일 작업의 시간까지 분할했다고 해석하지 않는다.
- 신규/구형 클라이언트의 PvP 요청을 세 배속·세 난수로 각각 검증했고, 최종 Chromium의 PvP 전투→서버 검증→양쪽 전적→복귀→재접속과 15적/소환수 시작·표시 검사를 통과했다. 마지막 시작 큐 대기 방식 변경 후에도 물량전 단일 흐름을 다시 통과했다.

- 15명+디안 소환수의 Chromium 실제 표시 객체 검사: 적 15명의 체력 바를 각 120번 진행해도 정지 채움 재그리기는 0회, 폭주 복제는 적마다 12회다. 사망 애니메이션 정지·안내 중 재소환 배율도 유지했고 화면을 캡처해 확인했다.
- 변환 검사는 부모 회전·비균등 배율·shear·좌우 반전에서 이전 방식과 같은 좌표를 확인한다. 24겹을 그려도 본체 행렬 계산은 한 번이며 두 uniform 배열을 다음 draw에 재사용한다. WebGL 복구·pipeline 복원 검사도 통과했다.
- PvP는 지원·회복 궁극기의 양쪽 발동과 기존 PvE 조건을 검사한다. 실제 BattleScene 기록을 세 배속·세 난수에서 저장 후 서버 재현했고, 수동 입력 위조는 거절했다. 격리 PostgreSQL의 실제 PvP 검증·양쪽 전적/점수 원자 저장·재전송·랭킹/보상 검사를 통과했다.
- 실제 모바일 기기 FPS 개선율은 측정하지 않았다. 수치는 제거된 재그리기/행렬/복제 작업에 대한 결과이며 전체 렉이 없어졌다는 보장은 아니다. 같은 고정 스텝 안의 처리 순서·편성·속성·난수까지 완전히 동일한 승률을 보장한다는 뜻도 아니다.
- SQL·저장 버전 변경과 운영 데이터 수정은 없다. 기존 전적·점수·미확정 전투를 추측해 소급 보정하지 않는다.
