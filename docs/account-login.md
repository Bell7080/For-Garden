# 계정 로그인과 연동

한 계정은 Supabase Auth 사용자 하나다. 저장·길드·친구는 UID에 연결되며, 같은 계정에 로그인 수단을 추가할 때 진행을 옮기거나 합치지 않는다. 구현의 기준은 `src/api/SupabaseAccountApi.ts`, `src/server/accountEntry.ts`, `src/api/webOAuth.ts`다.

## 현재 지원 경로

| 경로 | 동작 |
| --- | --- |
| 게스트 | 익명 가입. `is_anonymous`를 우선하고, 구형 응답은 비어 있지 않은 이메일로 판정한다. |
| 아이디 가입·연동 | `/api/account`가 새 UID를 만들거나 Bearer로 확인한 현재 UID에 아이디·비밀번호를 추가한다. 아이디 입력으로 기존 UID를 덮어쓰지 않는다. |
| 아이디 로그인 | `/api/account`가 아이디 별칭의 UID와 현재 Auth 이메일을 확인하고 비밀번호를 검증한다. 클라이언트가 예전 합성 이메일을 먼저 인증하지 않는다. |
| Google·Apple 로그인 | PKCE OAuth로 로그인한다. 다른 UID로 로그인하면 계정 전환 경계를 거친다. 제공자 설정이 없으면 지원되지 않는 것으로 처리한다. |
| Google·Apple 연동 | 설정에서 현재 UID에 identity를 추가한다. 연동 실패를 다른 계정 로그인으로 대체하지 않는다. |
| 이메일 | 로그인 OTP와 현재 계정의 이메일 변경 OTP를 구분한다. 확인 응답의 UID가 다르면 기존 세션을 덮지 않는다. |
| 연동 해제 | 마지막 로그인 수단은 해제할 수 없다. 이메일·비밀번호는 소셜 해제 화면에서 삭제하지 않는다. |

아이디 별칭은 `account_login_ids`가 소유한다. 실제 이메일이 바뀌어도 별칭은 같은 UID를 가리키며, 기존 ID·다른 UID의 ID를 덮어쓰지 않는다. 합성 도메인 `id.forgarden.app`은 기존 계정 식별에 사용되므로 변경하지 않는다.

## 인증·진행 경계

- 아이디는 영문 소문자로 시작하는 4~20자 영문·숫자·밑줄이며 대소문자를 구분하지 않는다. 비밀번호는 8~64자이고 아이디와 같을 수 없다. 원본은 `core/accountCredentials.ts`다.
- 비밀번호는 저장·로그하지 않는다. 가입과 로그인은 별도 속도 제한을 사용하고, 서버의 `Retry-After`를 따른다. 거절된 재시도로 대기 시간을 계속 늘리지 않는다.
- 가입 성공 후에는 비밀번호로 새로 로그인해 UID를 확인한다. 관리자 비밀번호 변경으로 폐기될 수 있는 구형 refresh 토큰을 재사용하지 않는다. 가입 후 로그인만 실패한 경우 확인된 UID의 로그인만 재시도한다.
- 일시적 네트워크 오류·429로 기존 게스트 토큰을 폐기하지 않는다. 실제 폐기된 refresh 응답과 구분하며, 새 토큰 저장에 실패하면 메모리 계정을 먼저 바꾸지 않는다.
- 회원가입·같은 UID 연동은 기존 진행을 유지한다. 다른 계정 로그인은 확인 후 성공했을 때만 연결을 내리고 Boot에서 서버 진행을 다시 읽는다. 취소·실패로 게스트 저장을 지우거나 두 진행을 자동 병합하지 않는다.
- OAuth는 PKCE S256과 메모리의 verifier를 사용한다. callback 메시지는 같은 origin·실제 팝업 창을 확인하고, 처리 후 주소를 비운다. 토큰을 `postMessage`하지 않는다.
- 타이틀은 인증 성공 후 별도의 새 pointerdown→pointerup 입력을 받아 진입한다. 이전 인증 세대·씬의 늦은 응답, 인증 전 시작된 터치, 손 떼기만 있는 입력, 중복 이벤트는 진입을 확정하지 않는다. 서버 세대 변경은 Boot에서 처리한다.
- 토큰은 Session/SaveData에 포함하지 않는다. 웹의 출시 전 임시 저장 예외와 네이티브 저장소 요구는 [출시 차단 목록](release-fixture-cleanup.md)이 소유한다.

## 약관·탈퇴

최초 로그인과 기존 계정의 동의 확인은 `LegalConsentManager`와 서버의 `record_legal_consent`를 통한다. 문서 버전·만 14세 확인·동의 시각을 서버에 남긴다. 탈퇴는 `request_account_deletion`으로 요청하고 이 기기에서 로그아웃한다. 유예는 7일이며, 유예 중 다시 로그인하면 취소 경로를 거친다. 실제 유예 만료 삭제 실행 여부는 DB 함수 생성과 별개이므로 [적용 기록](migrations-2026-10-29.md)을 확인한다.

## 배포 설정과 남은 확인

DB 계약은 `account_registration`, `account_identity_aliases`, `legal_privacy_deletion` 마이그레이션과 [적용 이력](../supabase/README.md#적용-이력)을 따른다. 아이디 가입은 서버 관리자 경계가 맡으므로 과거 클라이언트 `/auth/v1/signup`을 위해 메일 확인을 끄라는 절차를 현재 가입 구현에 적용하지 않는다.

소셜·이메일은 코드 구현만으로 실제 제공자 설정 완료를 뜻하지 않는다. 대상 환경에서 다음을 따로 확인한다.

1. Google/Apple 제공자 자격 증명과 Supabase callback 주소, 게임 origin의 `?pf_auth_callback=1` redirect 허용.
2. 수동 identity linking 설정. 프리뷰는 사용할 origin만 명시적으로 등록한다.
3. 실제 SMTP와 OTP 템플릿의 `{{ .Token }}`. 합성 이메일에는 메일함이 없으므로 이메일 변경 정책이 기존 주소 확인을 요구하는지 확인한다. 새 이메일 인증은 생략하지 않는다.
4. 게스트→아이디→소셜→이메일→다른 기기 아이디 로그인과 마지막 로그인 수단 보호를 실제 계정으로 확인한다. 이번 문서 정리에서 운영 제공자 설정이나 실제 계정 로그인을 수행하지 않았다.

아이디만 있는 계정은 메일 기반 비밀번호 복구가 없다. 실제 이메일을 인증·연동하는 경로와 혼동하지 않는다.

회귀 검사는 `accountRegistrationServer`, `accountIdentity`, `supabaseAccountApi`, `accountSwitch`, `accountSaveSync`, `titleEntryGesture`, `legalConsent` 단위 검사와 관련 E2E가 소유한다. 과거 실행 회수·스크린샷 메모를 현재 구현 상태의 근거로 사용하지 않는다.
